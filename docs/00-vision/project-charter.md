# 다이달로스 프로젝트 헌장

상태: D1 엔진 구축 중·제품 인수 미통과 · 갱신: 2026-10-16

## 존재 이유

다이달로스(Daedalus)는 1인 개발자가 AI와 함께 높은 품질의 2D·3D 게임을 제작할 수 있도록 설계하는 독립 게임 엔진이다. 코드, CLI, MCP, DCC 에셋 파이프라인과 사람이 직접 보는 실행 창을 주요 접점으로 삼는다.

단순히 복셀을 표시하거나 타일을 움직이는 기술 시연을 완성으로 보지 않는다. 조작, UI, 액션, 애니메이션, 오디오, 로딩, 네트워크, 저장, 배포와 디버깅을 포함하는 엔진 역량을 목표로 한다. 기능별 지원 수준은 [범위표](feature-quality-matrix.md)로 정의한다.

| 작업 방식 | MD 계획·아키텍처를 먼저 정리, 주기적으로 커밋 | 설계 게이트 이후 구현 착수 시점 |

추가 확정: 2D는 픽셀·고해상도 표현 모두, 3D는 복셀·일반 오픈월드 모두 포함한다. 웹 배포·설치형 배포·오픈소스 엔진 버전 관리가 필요하다. 웹·설치형은 기능·저장 형식·script API를 유지하고 기기별 화질 조정은 허용한다. 웹은 쉽게 내보낼 수 있는 HTML/Wasm 배포를 뜻하며 호스팅 서비스 개발 요청이 아니다.

스크립트는 C#을 주 언어로 결정했다. 기술 기준선은 C# 14/.NET 10 LTS/CoreCLR이며 PC 다운로드형 플러그인 확장을 우선 설계한다. 모드의 웹·모바일 실행 방식은 현재 PC 선택을 제약하지 않으며 후속 플랫폼 설계로 남긴다. 엔진에 V8·Chromium을 포함하지 않는다. [ADR-0003](../05-decisions/0003-csharp-and-native-gameplay.md)

오토파일럿은 플레이 조작·관찰·검증과 새 C# 게임 로직 주입 모두 필요하다. Rust 게임플레이는 안정성을 위해 빌드·재시작으로 반영하고 C#이 hot-reload 경로를 담당한다. Rust 코어에 C++ 부품을 연결할 수 있으나 두 코어를 중복 구현하거나 모든 native 모듈을 실행 중 교체한다는 요구는 아니다.

기준 개발 장비는 사용자의 현재 MacBook Pro: Apple M3 Pro, CPU 12코어(성능 6·효율 6), GPU 18코어, 통합 메모리 18GB, 내장 화면 3024×1964이다. 2026-10-15 로컬 시스템 정보로 확인했다. 화면 해상도가 벤치마크의 내부 렌더 해상도로 확정된 것은 아니다.

## 품질을 해석하는 기준

언급한 게임은 선호와 목표를 전달하는 참조이다. 게임 전체를 복제하거나 엔진 하나가 같은 완성도에 자동으로 도달한다고 해석하지 않는다. 각 참조를 재질, 그림자, 색·노출, 캐릭터, VFX, UI, 카메라, 조작 반응 등의 관찰 가능한 항목으로 분해한다. 어떤 항목을 어떤 플랫폼에서 충족해야 하는지 사용자와 합의한다.

스타일라이즈드와 사실적 표현은 서로 다른 재질·라이팅·포스트프로세싱 설정을 요구할 수 있다. 공통 엔진이 이를 확장 가능한 방식으로 수용하는 것이 목표이며, R01에서 단일 렌더 기법을 정답으로 고정하지 않는다.

## 현재 작업의 경계

사용자가 전체 목표를 재확인했다. **D1 AI-driven 제작용 엔진 → D2 해당 엔진을 사용하는 Minecraft급 3D 게임 → D3 같은 엔진을 사용하는 Terraria급 2D 게임**을 순차 인수한다. 현재는 D1 미완료다. 엔진 repository에는 게임을 넣지 않으며 D1 이전에 두 게임 제작으로 건너뛰지 않는다. [제품 인수표](../04-plan/product-delivery-and-acceptance.md)와 ADR-0005가 완료 기준이다.

설계와 [구현 체크리스트](../04-plan/implementation-checklist.md)를 기준으로 실제 런타임·도구·통합을 구축한다. 외부 게임 제작에는 공개 에셋/텍스처를 사용할 수 있으며 출처·재배포 조건을 기록한다. 작은 엔진 테스트 장면은 하위 시험 근거이며 전체 엔진·두 게임 완성을 대신하지 않는다. 콘솔 SDK 등 접근하지 못한 플랫폼·상용 품질·144fps를 구조만으로 지원/달성했다고 표시하지 않는다.

개발 중 반복되는 검증·변환·binding·AI 수정/실행/관찰·배포 작업을 공통화하고 자동화한다. 최적화 대상을 CI cache나 runtime 성능만으로 좁히지 않는다. 정확성·효과·한계를 [개발 파이프라인](../04-plan/development-iteration-pipeline.md)에 남긴다.

## 설계 완료의 의미

모든 미래 문제를 미리 해결했다고 선언하지 않는다. 핵심 결정에 근거·비교·실험 계획이 있고, 소유권·실패·플랫폼·성능 계약을 리뷰할 수 있으며, 미결 사항의 영향과 처리 시점을 아는 상태를 설계 게이트의 목표로 한다. 코드로만 확인할 수 있는 가설은 이후 최소 기술 실험으로 검증하고 명세를 갱신한다.
