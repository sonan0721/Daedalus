# 상용 엔진 공개 자료에서 배울 원칙

상태: R01은 공식 세션 개요 확인. 강연·슬라이드 전체 분석 미완료 · 2026-10-15

## 근거의 범위

Bungie의 GDC 2015 발표 개요는 작업 그래프 중심 실행, job fibers, 데이터 생성·접근·파괴 시점 검증을 설명한다. 발표 대상은 당시의 **Destiny**다. 이것으로 Destiny 2의 현재 엔진 구조를 동일하다고 판정하지 않는다. [Bungie 발표](https://www.gdcvault.com/play/1022164/Multithreading-the-Entire-Destiny)

Blizzard의 GDC 2017 발표 개요는 Overwatch의 ECS 기반 게임플레이와 네트워크 시뮬레이션을 설명한다. 공개 개요만으로 “worker 1은 청크, worker 2는 물리” 같은 고정 스레드 배치를 추론하지 않는다. [Blizzard 발표](https://www.gdcvault.com/play/1024001/-Overwatch-Gameplay-Architecture-and)

## 다이달로스 적용 제안

| 배울 문제 | 엔진 적용안 | 검증할 질문 |
| --- | --- | --- |
| 작업 사이의 의존성과 수명 | 시스템 read/write 계약 + 명시적 tick 경계 | 쓰는 동안 다른 시스템이 읽는 데이터는 무엇인가? |
| 고정 담당 스레드의 병목 | 짧은 CPU 작업과 소유자가 필요한 전용 실행을 구분 | 물리·스크립트·meshing이 서로 굶기지 않는가? |
| 시뮬레이션·표시의 중첩 | 렌더 전용 데이터 게시와 독립 UI 상태 | 새 tick이 없을 때 무엇을 갱신할 수 있는가? |
| 네트워크와 ECS의 연결 | 권한 있는 명령·안정 ID·복제 모델을 조기에 설계 | 로컬 게임 로직과 서버 로직의 의미가 같은가? |
| 복잡성의 통제 | 데이터·자원 상태를 trace와 검증 모드로 노출 | 잘못된 수명을 디버그 빌드에서 탐지 가능한가? |

이 표는 발표의 코드를 재현한 설계가 아니다. 공개 근거에서 얻은 문제의식을 다이달로스의 요구에 맞게 옮긴 제안이다.

## 후속 상세 조사

- 전체 발표·슬라이드에서 실제 barrier, 작업 granularity, 수명 검증 규칙을 시간 또는 페이지와 함께 추출한다.
- 당시 플랫폼의 전제와 macOS·브라우저·1인 유지보수 환경의 차이를 명시한다.
- 특정 큐·executor·ECS를 고르는 근거로 삼으려면 실제 후보 소스와 비교한다.
- 상용 게임의 렌더 프레임·로딩 UI가 동작하는 관찰과 내부 구현 증거를 구분한다.

## 이 문서가 막는 오류

상용 엔진의 이름을 성능 보증서처럼 사용하지 않는다. 다이달로스의 응답성과 품질은 자체 플랫폼·워크로드·측정 결과로 평가한다. 멀티스레드 수, 코어 사용률, ECS 엔티티 수 하나만으로 동일한 아키텍처나 품질을 선언하지 않는다.
